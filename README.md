# SNS Blocker Web

SNS などのアプリを、決めた時間だけ使えなくする Web アプリ（スマホ向け）。

- ブロックはサーバー（cf-rules-api）がユーザーの Cloudflare Zero Trust に反映し、スマホの 1.1.1.1 アプリ（WARP）の通信で効く
- 使い方は「**自分でロック**」と「**固定時間で自動ロック**」の2つから選ぶ
- どちらも、続けるとキャラクター（スライム）の色が変わる（21日で銀色、さらに続けると王冠）

## 起動方法

```bash
npm install
npm run dev
```

`.env` が無い間は、**モック**（ブラウザ内の仮サーバー。[サーバーとのやりとり](#サーバーとのやりとり)の決まりどおりに応答する）で動く。

### 本物のサーバーにつなぐ

プロジェクト直下に `.env` を作って次の2行を書く。

```
VITE_API_BASE=/api
API_PROXY_TARGET=http://localhost:8787
```

- `VITE_API_BASE`: API の場所。仕様どおり画面と同じオリジンの `/api` 以下
- `API_PROXY_TARGET`: 開発サーバー（Vite）が `/api` と `/auth` を流す先（[`vite.config.js`](vite.config.js)）。手元の cf-rules-api（`uv run pywrangler dev`）なら `http://localhost:8787`。デプロイ済みのものの URL はバックエンド担当に聞く
- ログインは Cookie（`session`）で続くので、画面と API を同じオリジンに見せる必要がある（cf-rules-api の README の決まり）
- **ログイン画面はまだサーバーにつないでいない**。今のサーバーは偽の Google ログインだけなので、ブラウザで `http://localhost:5173/auth/google/start` を一度開くと、テスト用のユーザーでログインした状態（Cookie）になる

### スマホで試す

```bash
npm run dev -- --host
```

表示された `Network: http://192.168.x.x:5173/` をスマホのブラウザで開く（スマホと PC は同じ Wi-Fi に接続）。
http で開いても動くように、ID の生成などは https 専用の機能（`crypto.randomUUID` など）に頼らない作りにしている（[`src/utils.js`](src/utils.js)）。

### 開発中だけのテスト用ボタン

`npm run dev` の時だけ、メイン画面に 🧪 のボタンが出る（本番のビルドには入らない）。

| モード | ボタン |
|---|---|
| 自分でロック | コイン+10・1日成功・1日失敗 |
| 固定時間 | コイン+15・1日成功・1日失敗・承認できる時刻にする（翌朝まで待たずにキャンセルや設定の承認を試す） |

## 使い方のモード

ログインの後、最初にどちらかを選ぶ（[`src/pages/ModeSelect.jsx`](src/pages/ModeSelect.jsx)）。2つのモードは**まったく別**で、コインもスライムの成長も別に持つ。

| | 自分でロック（`timer`） | 固定時間で自動ロック（`fixed`） |
|---|---|---|
| 向いている人 | これから勉強・集中したい時に、その場でロックしたい人（始める時は本人のやる気しだい） | 毎日の習慣にしたい人（決めた時間は勝手にロックされる） |
| ロックのしかた | 使いたくない時に、アプリと時間を選んで自分でロック | 曜日・時間帯・アプリの「予定」を決めておくと、毎週その時間は自動でロック |
| 成功の日 | 1日の目標時間ロックできた日 | 予定のある日のうち、一時解除を使わなかった日（予定の無い日は数えない） |
| 失敗を守る | お休みチケット（週1枚無料＋🪙10で購入） | **無い** |
| 途中で外す | できない | 一時解除チケット（🪙15・3枚まで）で一時解除できる。使った日は失敗 |
| コイン | ロックをやりきると 10分で1枚 | 一時解除なしでやりきった予定の長さぶん 10分で1枚 |
| コインの使い道 | お休みチケット | 一時解除チケット |
| 色・王冠 | [スライムの成長](#スライムの成長2つのモードで共通)のとおり | 同じ |

### モードを変える

- **自分でロック → 固定時間**: いつでもできる（メニューの「固定時間で自動ロックにする」）。固定時間を始めた時点で、自分でロックのコイン・スライムの成長・ロック中の表示はリセットされ、固定時間のルールで育ち直す
- **固定時間 → ほかのモード**: 直接はできない。メニューの「固定時間をキャンセル」で申請し、**翌朝以降に承認した時点で**予定が消え、もう一度モードを選ぶ（固定時間を選んだら、予定を決めるところから）
- キャンセルを申請しても、承認するまでは予定どおりロックされる。承認しないまま期限を過ぎると、キャンセルは取り消されて予定が続く（その時はお知らせを出す）

### 画面のつながり

| 状態 | 開く画面 |
|---|---|
| ログインしていない | `/` 説明ページ（準備 → 使い方 → アカウント。準備は Cloudflare への登録・1.1.1.1 アプリ・証明書の案内で、登録ページやアプリのストアへのリンク付き）。一度説明を見た端末はログイン画面から（「戻る」で説明も見られる）。初めての端末でも右上の「ログイン」で説明を飛ばせる |
| ログイン済み・モード未選択 | `/mode` モード選択 |
| 自分でロック | `/home` → `/select-app` → `/confirm`、`/stats` まとめ |
| 固定時間（始める前） | `/fixed-setup` 予定を決める |
| 固定時間（始めた後） | `/home`（固定時間のメイン画面）。自分でロック用の画面と `/fixed-setup` は開かない |

画面の振り分けは [`src/App.jsx`](src/App.jsx)（`Entry` / `RequireMode` / `RequireNotFixed`）。

## 自分でロック

```
スマホ（このアプリ）                     サーバー（cf-rules-api）        保存先（未定）
 ① アプリ・時間を選ぶ（目的は1日の目標と一緒に決めておく）
 ② スタート ── アプリごとにタイマーを開始 ─▶ Cloudflare に反映
             ◀──── 終わる時刻 ─────────
 ③ 記録を送る ──────────────────────────────────────────────▶ 保存
 ④ カウントダウン表示（サーバーの時刻基準）
 ⑤ 終了 → 「おめでとう！」＋コイン付与
 ⑥ まとめ画面 ◀──────────── 期間を指定して記録を取得 ─────────── 
```

| 項目 | ルール | 場所 |
|---|---|---|
| ロック | 一度始めたロックは**キャンセルできない**。スマホからは止める操作を送らない | [`src/pages/Confirm.jsx`](src/pages/Confirm.jsx) |
| 1回のスタート | 複数のアプリを選べ、アプリごとに時間が違ってもよい（20 / 30 / 60 分、またはカスタムで 1〜1440 分） | [`src/pages/AppSelect.jsx`](src/pages/AppSelect.jsx) |
| ロック中のアプリ | ロック追加で選べない（サーバーで、動いているタイマーをもう一度始めないため） | `AppSelect.jsx` |
| 目的 | 何のためにロックするか（勉強・仕事・読書・運動・睡眠・自由入力）。**1日の目標を決めた直後に続けて聞き、ロックのたびには聞かない**。スキップでき（目的なし）、メニューの「1日の目標と目的」で変えられる。メイン画面の「今日の目標」の横と最終確認に「◯◯のため」と出す。サーバーには送らず、保存先の記録にだけ付ける（`habit.purpose`） | [`src/components/PurposeSheet.jsx`](src/components/PurposeSheet.jsx) |
| コイン | **10 分ごとに 1 枚**。1 回のスタートで複数アプリをロックした時は、**一番長い制限時間**で計算する（例: 30 分 + 60 分 → 6 枚）。そのスタートのロックが全部終わった時に付与する | [`src/data/apps.js`](src/data/apps.js) `coinsFor` / [`AppContext.jsx`](src/store/AppContext.jsx) |
| 1日の目標 | 1 日にロックする時間を決める（30分 / 1時間 / 1時間30分 / 2時間 / 3時間 / カスタム 10〜720 分）。初めてメイン画面を開いた時に決め、メニューの「1日の目標」で変えられる。変えた目標は今日の判定から使う | [`src/pages/Home.jsx`](src/pages/Home.jsx) |
| 1日の成功 | その日（0時〜24時、端末の時間帯）にロックした時間の合計が目標以上なら成功。**実際に経過した分だけ**数える（60分のロックを始めた直後は 0 分）。同じ時間に複数のアプリをロックしても二重に数えない（30分×3アプリ＝30分）。日をまたぐロックは 0 時で分けて両方の日に数える | [`src/habit.js`](src/habit.js) |
| 判定のタイミング | 今日の分は、経過した時間が目標に届いた時点ですぐ成功にする。届かなかった日は、日付が変わってから失敗として判定する。アプリを開かなかった日も、次に開いた時に 1 日ずつまとめて判定する | `AppContext.jsx` |
| 判定に使う記録 | 保存先の記録（`fetchRecords`）。モックのデモデータは使わない（`allowDemo: false`） | `AppContext.jsx` |
| お休みチケット | 目標に届かなかった日に自動で使い、その日は何も起きない（色も連続記録もそのまま）。**無料**: 1 週間（月曜〜日曜）に 1 枚、持ち越しなし。**コインで買う**: 1 枚 🪙10（`TICKET_PRICE`）、3 枚まで（`MAX_EXTRA_TICKETS`）。メイン画面の 🎫 から買う。使う順は無料 → 買った分。使った時はスライムがチケットを食べる | `habit.js` / `Home.jsx` |
| 今日の表示 | メイン画面のカードのいちばん上に「今日の目標 ◯ / ◯分」とバーを大きく出す。濃い部分は経過した分、しま模様は今のロックが終わるまでに増える分。下に今の状況を一言で出す（「あと◯分 ロックすると今日の目標を達成」「ロック中… あと◯分で達成」「ロック中。終わってもあと◯分 足りません」「✓ 今日の目標を達成しました」） | `Home.jsx` |
| アカウントごとのデータ | コイン・ロック中のアプリ・カスタムアプリ・毎日の目標はアカウントごとに分けて端末に保存する。ログアウト中もロックはサーバー側で続き、次にログインした時に終了処理（「おめでとう」とコイン付与）をする | `AppContext.jsx` |

- 判定の状態はアカウントごとに `habit`（`goal` / `purpose` / `stage` / `progress` / `streak` / `settledUntil` / `ticketsUsed` / `extraTickets` / `failing`）として保存する
- まだ知らせていない判定の結果は `habitEvents` として保存する（アプリを閉じても消えない）。お知らせの「OK」で空にする。食べたチケットには `eaten: true` を付ける

## 固定時間で自動ロック

ルール: [`src/fixed.js`](src/fixed.js) / 状態と操作: [`src/store/useFixedMode.js`](src/store/useFixedMode.js) / 画面: [`FixedSetup.jsx`](src/pages/FixedSetup.jsx)・[`FixedHome.jsx`](src/pages/FixedHome.jsx)

### 予定を決める

予定は「曜日（複数可）・時間帯・アプリ（複数可）」の組で、いくつでも作れる。例: 「火 2:00〜3:00 YouTube」「水 12:00〜その日の終わり X」「毎日 22:00〜翌7:00 YouTube・TikTok」。

入力を減らすための工夫:

- 曜日は「毎日」「平日」「土日」のボタン1つで入る（1日ずつ足し引きもできる）
- 時間帯は「夜」「朝」「日中」「夕方」「1日中」のボタンで入り、細かい時刻は時刻の入力で直す。「その日の終わりまで」ボタンもある
- 予定が無い時は「毎日 22:00〜翌7:00」「平日 9:00〜17:00」から始められる
- 予定の「コピー」で、アプリと時間帯はそのままに曜日だけ違う予定を作れる
- 決めている途中の予定は保存しておくので、画面を閉じても消えない

「その日の終わり」は **23:59** まで（サーバーの時刻は 00:00〜23:59 しか書けず、開始と終了を同じにもできないため。23:59〜0:00 の1分は止まらない）。始めた後は予定を変えられない（変える時はキャンセルしてから決め直す）。

### 始めた後のルール

| 項目 | ルール |
|---|---|
| 成功の日 | 予定のある日だけ数える。その日の予定が全部終わってから判定し（日をまたぐ予定は翌日に終わってから）、一時解除を使わなければ成功、使ったら失敗。モードを始める前に終わっていた予定は数えない |
| 失敗 | お休みチケットは無いので、そのまま失敗（色の下がり方は[スライムの成長](#スライムの成長2つのモードで共通)と同じ） |
| コイン | 一時解除なしでやりきった予定の長さぶん、10分で1枚。その日の判定の時にもらう（失敗した日も、一時解除と重ならなかった予定のぶんはもらえる） |
| 一時解除チケット | 1 枚 🪙15（`UNLOCK_PRICE`）、3 枚まで（`MAX_UNLOCK_TICKETS`）。予定の時間中だけ使え、使うとすべてのロックが一定時間解除される（今は 30 分。[サーバーとのやりとり](#固定時間で自動ロック-1)を参照） |
| 一時解除の記録 | いつ使ったかはこの端末で覚え、成功・失敗の判定に使う |
| キャンセル | [モードを変える](#モードを変える)のとおり |
| 目的 | 「この予定で始める」を押した後、確認の前に一度だけ聞く（自分でロックと同じ選択肢・スキップ可）。メイン画面の「今日のロック」の横に「◯◯のため」と出す。ブロックの決まりには関係しないので、始めた後もメニューの「目的」で変えられる |

メイン画面には、今日の予定（ロック中は残り時間）、一時解除チケットの枚数と「一時解除する」ボタン、連続日数と21日の道のりを出す。承認待ちの変更（キャンセル・一時解除の設定）がある時は、いつから承認できるかと「承認する」ボタンを出す。

保存する状態（アカウントごとの `fixed`）: `schedule`（予定）/ `ruleIds`（予定ごとのサーバーのルール）/ `purpose`（目的）/ `habit` / `events`（まだ知らせていない判定の結果）/ `coins` / `unlockTickets` / `unlocks`（使った一時解除）/ `unlockMinutes`（今サーバーで効いている一時解除の長さ）/ `pending`（承認待ちの変更）/ `cancelling` / `notice`。決めている途中の予定と目的は `fixedDraft`。

## スライムの成長（2つのモードで共通）

ルール: [`src/habit.js`](src/habit.js) / 表示: [`src/components/habitUi.jsx`](src/components/habitUi.jsx)（21日の道のり・結果のお知らせ）

| 項目 | ルール |
|---|---|
| 色の段階 | 水色 → 緑 → 青 → 紫 → **銀**（`COLORS`）。大きさは一定 |
| 進化 | 連続で成功して、**3日・7日・14日・21日**目に 1 つ上の色になる（`STEP_DAYS` = 3, 4, 7, 7 日ずつ）。上がる時にジャンプする |
| 退化 | 失敗したら（自分でロックではお休みチケットが無い時）、1 つ下の色に戻り、連続記録と次の色までの日数は 0 に戻る。水色より下にはならない |
| 失敗が続いた時 | **下がるのは最初の 1 回だけ**。その後も失敗が続く間は色はそれ以上下がらず、お休みチケットも使わない（守るものが無いため）。次に成功すると普通に戻る。毎日アプリを開いて失敗しても、開かずに放っておいても結果が同じになる（「失敗した日は開かない方が得」にならない） |
| 銀色の後 | 毎日の判定は続く。失敗すると紫に戻る |
| 王冠（隠し要素） | 銀色になってから `CROWN_DAYS`（3）日続けて成功すると、スライムが王冠をかぶる（`hasCrown`）。お休みチケットの日は外れないが日数にも数えない。失敗して紫に戻ると外れ、また銀色になってから3日で再びかぶる。**ユーザーには何も知らせない**（お知らせ・説明文・ふりかえりに出さない） |
| 進化までの道のり | 21 日分のマスを並べ、色が変わる日（3・7・14・21 日目）に次の色の丸を置く。達成した日はその区間の色で塗り、今日のマスは点滅させる。横に「あと ◯日 で ●紫」と出す |
| 結果のお知らせ | 判定の結果はポップアップで知らせる。見出しは中身に合わせる（✨ 進化した！ / 💧 色が1つ戻りました / 🎯 今日の目標を達成！（固定時間では「一時解除なしでやりきった！」）/ 🎫 お休みチケットで守りました / 💧 目標に届きませんでした（固定時間では「一時解除を使いました」）/ 📅 前回からの結果）。失敗が続いた日は「10/24〜10/28 …」のように 1 行にまとめる。固定時間ではもらったコインも出す |

判定は端末で行っている。保存先ができたら、ここもサーバー側で持つのが望ましい（端末の時計を変えると判定をごまかせるため）。

## サーバーとのやりとり

実装: [`src/api.js`](src/api.js)

取り決めは `seikatsukan/api-spec` の `openapi.yaml`（v0.2.0 の案）。**バックエンドは変えられないので、こちらが合わせる。**

### 共通の決まり

| 決まり | 内容 |
|---|---|
| 場所 | 画面と同じオリジンの `/api` 以下 |
| ログイン | `/auth` 以下で付く Cookie `session`（`fetch` が自動で送る）。無い・切れている時は 401 `UNAUTHORIZED` |
| 項目名・時刻 | JSON は camelCase、時刻は `2026-10-30T21:30:00+09:00` の形 |
| エラー | 常に `{ "code", "message", "details" }`。`message` はそのまま画面に出せる日本語なので、そのまま表示する |
| 変更の反映 | 作る・厳しくする変更はすぐ反映。緩める変更（消す・オフにする・一時解除の設定を甘くする）は**反映待ち**になり、翌朝以降に本人が承認した時点で反映する。承認しないまま期限を過ぎたら消える |

### アプリの指定（`target`）

サーバーのカタログ（`GET /options` の `apps`）にあるアプリは **ID** で、無いアプリは **ドメイン** で送る。どちらのモードでも同じ。

| アプリ | 送る `target` |
|---|---|
| YouTube / TikTok / Instagram / X | `{"type": "sites", "apps": ["youtube"], "domains": [], "categoryIds": []}`（ID は `displayName` が同じものを探す） |
| Facebook / Threads（カタログに無い） | `{"type": "sites", "apps": [], "domains": ["facebook.com"], "categoryIds": []}`（[`apps.js`](src/data/apps.js) の `DEFAULT_APPS` のドメイン） |
| カスタムアプリ | `{"type": "sites", "apps": [], "domains": ["line.me"], "categoryIds": []}`（入力されたドメイン。`https://`・`www.`・パスを取り除いた形） |

ドメインで送ると、そのドメインとサブドメインだけが止まる。カタログのアプリは画像・動画を配る別のドメインまで止まるので、ドメインで送るアプリはアプリの一部が使えてしまうことがある。

### 自分でロック

サーバーには「今からこのアプリを○分」という API は無く、「ルール（対象と時間の決め方）を作る」「timer のルールを始める」が別々にある。そこで**アプリごとに timer のルールを1つ作り、ロックのたびに選んだ分数で始める**。

1. `GET /options`・`GET /rules`・`GET /status` を同時に呼び、アプリ ID・今あるルール・サーバーの現在時刻を取る
2. 選んだアプリのうち、**ロック中（`timerEndsAt` が未来）のものが1つでもあれば何も始めずにエラー**。動いているタイマーをもう一度始めた時の動きは仕様に無いため（画面でも選べないが、別の端末で始めていた時のため）
3. まだルールが無いアプリだけ `POST /rules` で作る。オフになっているルールは `PATCH /rules/{ruleId}` で `{"enabled": true}` にする（どちらもすぐ反映）
4. アプリごとに `POST /rules/{ruleId}/timer` を `{"durationMinutes": 選んだ分数}` で呼ぶ。返ってきたルールの `timerEndsAt` が終わる時刻

- **ルールは消さない**。消すのは反映待ちになるため、毎回作って消す形にはしない。終わったタイマーのルールは、そのアプリを次にロックする時にまた使う
- 同じアプリかどうかは、ルールの名前ではなく `target` の中身（`apps` / `domains`）で見分ける
- カウントダウンは `timerEndsAt` を終わる時刻、そこから分数を引いた時刻を始まった時刻とする。スマホの時計がずれていてもよいよう、`GET /status` の `now` との差でずれを補正する（通信にかかった時間の半分も差し引く）

うまくいかなかった時:

| 場面 | 画面 |
|---|---|
| ロック中のアプリが含まれていた | 何も始めずに「○○ はすでにロック中です」 |
| カスタムアプリのルールを作る時に 422 `VALIDATION_ERROR` | 何も始めずにアプリ選択画面へ戻り、そのアプリの名前・ドメインの修正画面を開く |
| **一部のアプリだけタイマーを始められた** | 始められたアプリはロックとして登録する（始めたタイマーは止められないため）。確認画面には始められなかったアプリだけ残し、「○○ はロックを始めました。△△ は始められませんでした（理由）」と出して「もう一度試す」を押せるようにする |
| 1つも始められなかった | サーバーの `message`（例: 409 `CLOUDFLARE_NOT_CONNECTED` の「Cloudflare と連携してください」）を出して「もう一度試す」 |
| JSON の無い HTTP エラー | 「サーバーエラー (500)」 |
| 15 秒以内に応答が無い／つながらない | 「サーバーから応答がありません」／「サーバーに接続できません」 |

### 固定時間で自動ロック

| 場面 | 送るもの |
|---|---|
| 始める | ① `PATCH /settings` に一時解除の決まり `{"unlock": {"unlockMinutes": 30, "unlocksPerDay": 3, "delayedUnlockMinutes": null}}`（[`fixed.js`](src/fixed.js) の `UNLOCK_SETTINGS`）② 予定ごとに `POST /rules` で時間帯（`window`）のルール |
| 一時解除 | `POST /unlocks` に `{}`（全部のルール）。申請した時点でサーバーの今日の回数を1回使う |
| キャンセル | 予定のルールごとに `DELETE /rules/{ruleId}`。反映待ちになる |
| 承認 | `approvableFrom` を過ぎた反映待ちを `POST /pending-changes/{id}/approve` で1つずつ承認する |

予定1つ分のルール:

```json
{
  "name": "火 2:00〜3:00",
  "schedule": { "type": "window", "start": "02:00", "end": "03:00", "days": [2] },
  "target": { "type": "sites", "apps": ["youtube"], "domains": [], "categoryIds": [] }
}
```

- 1つの予定のアプリは1つのルールにまとめる。`days` は 0=日曜〜6=土曜、`end` が `start` より前なら日をまたぐ
- **一時解除の長さは1つだけ（30分）**。今のサーバーは申請の時に長さを選べず、長さはユーザーごとの設定1つで決まるため
- 一時解除の決まりは、**今の設定より緩いと反映待ち**になる（長くする・回数を増やす・待ち時間を短くする）。その間は今の設定のまま一時解除され、メイン画面に「承認待ち」を出す
- 途中で通信に失敗した時は、終わった分（設定・作ったルール）を覚えておき、「もう一度試す」では残りだけ送る（作ったルールを消すのは反映待ちになるので、二重に作らないように）

### モック

`VITE_API_BASE` が未設定の時は、[`src/api.js`](src/api.js) の中のモックが、上で使うエンドポイントに仕様どおりの形で答える（1回 0.25 秒）。

- データは `localStorage` の `sns-blocker:mock-api` に保存する（再読み込みしても、動いているタイマーや反映待ちが残る）
- カタログは cf-rules の `get_catalog()` と同じ（X・YouTube・Instagram・TikTok・LINE）
- ドメインの形が cf-rules の決まり（英小文字・数字・`-`・`_` を `.` でつないだもの）に合わない時は 422 `VALIDATION_ERROR`
- 動いているタイマーをもう一度始めると 409 `TIMER_RUNNING`（仕様に無いので仮。アプリからは呼ばない）
- 一時解除の設定の初期値は仕様書の例と同じ（1回10分・1日2回・待ち時間5分）。そのため固定時間を始めた時の設定は反映待ちになり、承認するまで一時解除は「5分待ってから10分」になる
- 反映待ちは翌朝 5:00 から承認できる（仕様では時刻は未決定）。期限は 24 時間
- **一部だけ失敗する場面を試す**: `localStorage` の `sns-blocker:mock-api-fail` に `["Facebook"]` のようにルール名を入れると、そのルールのタイマーを始める時に 502 `CLOUDFLARE_API_ERROR` を返す

## 保存先とのやりとり

実装: [`src/storage.js`](src/storage.js)

自分でロックの記録（まとめ画面と毎日の目標に使う）の保存先。保存先（DB・クラウドなど）は**未定**で、今は端末の `localStorage` に保存するモックで動いている。
保存先が決まったら、`saveRecord` と `fetchRecords` の中身を API 通信に置き換えるだけでよい（呼び出し側は変更不要）。

### 記録を送る `saveRecord(record)`

- **いつ**: サーバーでタイマーを始められた時（ロック開始時）。ロックはキャンセルできないので、開始時点で確定とする
- **単位**: ロックを 1 回スタートするごとに 1 件。複数アプリをまとめてロックした時は `apps` に並ぶ

| 項目 | 型 | 内容 |
|---|---|---|
| `id` | 文字列 | 記録 ID（スマホで作る UUID） |
| `userId` | 文字列 | ログイン中のアカウント ID（[アカウント（認証）](#アカウント認証)が返す `userId`） |
| `startedAt` | 日時文字列 | 開始日時（サーバーのタイマーの開始時刻） |
| `apps` | 配列 | ロックしたアプリ |
| `apps[].name` | 文字列 | アプリ名 |
| `apps[].minutes` | 数値 | 制限時間（分） |
| `purpose` | 文字列 / `null` | ロックを始めた時の目的（「勉強」「仕事」などや自由入力の文字。1日の目標と一緒に決めたもの）。目的なしの時は `null` |

```json
{
  "id": "db88aa66-5576-4251-978a-2d7eda1fefe8",
  "userId": "b7cb565a-d045-44d3-a2cf-8870fa536611",
  "startedAt": "2026-10-27T12:58:04.576Z",
  "apps": [
    { "name": "LINE", "minutes": 30 },
    { "name": "YouTube", "minutes": 20 }
  ],
  "purpose": "勉強"
}
```

- 各アプリの終了時刻は `startedAt + minutes` で求められるので保存しない
- 送信に失敗してもロックや画面表示は止めない（コンソールにエラーを出すだけ）

### 記録を取得する `fetchRecords({ userId, from, to })`

まとめ画面（今週 / 今月のグラフ、カレンダー）と毎日の目標の判定で呼ぶ。

| 引数 | 内容 |
|---|---|
| `userId` | このアカウントの記録だけ取得する |
| `from` | 期間の始まり（この日時を含む） |
| `to` | 期間の終わり（この日時を含まない） |

- `startedAt` が `from` 以上 `to` 未満の記録を、上の「送る記録」と同じ形の配列で返す
- 呼ばれ方: 週（月曜 0:00〜翌週月曜 0:00）、月（1 日 0:00〜翌月 1 日 0:00）、カレンダーの表示月。いずれも端末の時間帯で区切る
- 戻り値は `{ records: [...], demo: false }`。`demo` はモック専用で、保存済みの記録が 1 件も無い時に見た目確認用のデモデータを返したことを示す。本番の保存先では常に `false` でよい

## アカウント（認証）

実装: [`src/auth.js`](src/auth.js)

今は端末の `localStorage` にアカウントを保存するモックで動いている（パスワードは SHA-256 でハッシュ化して保存）。
**本番は Google ログイン**（cf-rules-api の `/auth/google/start`。画面ごと移動し、Cookie でログインが続く）になる予定で、ログイン画面はまだそれに合わせていない。

- **いつ**: 説明ページの Step 3 で「アカウントを作成」または「ログイン」を押した時
- **成功したら**: 返ってきた `userId` / `email` をログイン状態として端末に保存し、メイン画面へ進む
- **ログアウト**: メイン画面のメニューから。端末のログイン状態を消して説明ページに戻る

モックの送る内容と返す内容:

```json
{ "email": "test@example.com", "password": "password123" }
```

```json
{ "userId": "85e212bd-5eeb-42db-be42-e004749b19f6", "email": "test@example.com" }
```

| 場面 | 表示する文 |
|---|---|
| 新規登録で、パスワードが 8 文字未満 | （送る前にスマホで確認する） |
| 新規登録で、メールアドレスがもう使われている | このメールアドレスはすでに登録されています |
| ログインで、メールアドレスかパスワードが違う | メールアドレスかパスワードが違います |
| 通信そのものに失敗した | 通信に失敗しました。もう一度お試しください |

## JSON の例（自分でロック）

日時は日本時間（`+09:00`）で書いている。ルール ID などはサーバーが付ける値の例。

### 例 1: 初めて YouTube と Facebook をロック（目的あり）

YouTube を 30 分、Facebook を 20 分でスタートした場合（目的は「勉強」に決めてある）。どちらもまだルールが無い。

**① スマホ → サーバー**（`GET /options`・`GET /rules`・`GET /status` を同時に）

`GET /options` の応答（抜粋）

```json
{ "apps": { "youtube": { "displayName": "YouTube", "domains": ["youtube.com", "youtu.be"] } }, "categories": {}, "webPushPublicKey": null }
```

`GET /rules` の応答は `[]`、`GET /status` の応答（抜粋）は次のとおり。

```json
{ "now": "2026-10-30T21:00:00+09:00", "timezone": "Asia/Tokyo", "blockingRuleIds": [] }
```

**② スマホ → サーバー**（ルールを作る。`POST /rules` を1つずつ）

```json
{ "name": "YouTube", "schedule": { "type": "timer", "durationMinutes": 30 }, "target": { "type": "sites", "apps": ["youtube"], "domains": [], "categoryIds": [] } }
```

```json
{ "name": "Facebook", "schedule": { "type": "timer", "durationMinutes": 20 }, "target": { "type": "sites", "apps": [], "domains": ["facebook.com"], "categoryIds": [] } }
```

応答は `{ "applyMode": "immediate", "rule": { "id": "rule_3f9a1c", ... } }`。

**③ スマホ → サーバー**（タイマーを始める）

`POST /rules/rule_3f9a1c/timer`

```json
{ "durationMinutes": 30 }
```

応答（ルール。抜粋）

```json
{ "id": "rule_3f9a1c", "name": "YouTube", "enabled": true, "schedule": { "type": "timer", "durationMinutes": 30 }, "timerEndsAt": "2026-10-30T21:30:00+09:00", "pendingChange": null }
```

Facebook も同じように `POST /rules/{Facebook のルール ID}/timer` に `{"durationMinutes": 20}` を送る。

**④ スマホ → 保存先**（記録を送る）

```json
{
  "id": "6f1c2a9e-3b7d-4e2a-9c41-0a8f5d2b7e10",
  "userId": "b7cb565a-d045-44d3-a2cf-8870fa536611",
  "startedAt": "2026-10-30T21:00:00.000+09:00",
  "apps": [
    { "name": "YouTube", "minutes": 30 },
    { "name": "Facebook", "minutes": 20 }
  ],
  "purpose": "勉強"
}
```

### 例 2: 次の日にまた YouTube をロック（ルールを使い回す）

YouTube を 60 分、カスタムで追加した LINE（`line.me`）を 45 分でスタートした場合（目的は決めていない）。

- `GET /rules` に YouTube のルール（`timerEndsAt` は過去）があるので、作らずに `POST /rules/rule_3f9a1c/timer` に `{"durationMinutes": 60}` を送る
- LINE はカスタムなのでドメインで探す。まだ無いので `POST /rules` で `"target": {"type": "sites", "apps": [], "domains": ["line.me"], "categoryIds": []}` のルールを作ってから始める
- 保存先には `"purpose": null` で送る

### 例 3: ロック中のアプリが含まれていた

YouTube のタイマーが別の端末で始まっていた（`GET /rules` の YouTube のルールの `timerEndsAt` が未来）。

→ ルールを作ることもタイマーを始めることもせず、「YouTube はすでにロック中です」と出す。保存先には何も送らない。

### 例 4: 一部のアプリだけ始められなかった

YouTube は始められたが、Facebook の `POST /rules/{ruleId}/timer` が次のエラーを返した。

```json
{ "code": "CLOUDFLARE_API_ERROR", "message": "Cloudflare への反映に失敗しました。しばらくしてからもう一度お試しください", "details": { "retryable": true } }
```

→ YouTube はロックとして登録し、保存先にも YouTube だけの記録を送る。確認画面には Facebook だけを残して「YouTube はロックを始めました。Facebook は始められませんでした（Cloudflare への反映に失敗しました。…）」と出す。「もう一度試す」で Facebook だけを始め直す（別の記録になる）。

### 例 5: Cloudflare とまだ連携していない

最初のタイマーを始める時に 409 が返り、1つも始められなかった。

```json
{ "code": "CLOUDFLARE_NOT_CONNECTED", "message": "Cloudflare と連携してください", "details": null }
```

→ 「Cloudflare と連携してください」を出し、「もう一度試す」を押せるようにする。保存先には何も送らない。作ったルールはそのまま残り、次に使われる。

### 例 6: 保存先から記録を取得（まとめ画面）

10 月 26 日（月）〜 11 月 1 日（日）の「今週」を表示する場合。

**スマホ → 保存先**（取得の条件。`from` は含み、`to` は含まない）

```json
{
  "userId": "b7cb565a-d045-44d3-a2cf-8870fa536611",
  "from": "2026-10-26T00:00:00.000+09:00",
  "to": "2026-11-02T00:00:00.000+09:00"
}
```

**保存先 → スマホ**（`startedAt` が期間内の記録を、送った時と同じ形で返す。無い期間は `"records": []`）

```json
{
  "records": [
    {
      "id": "6f1c2a9e-3b7d-4e2a-9c41-0a8f5d2b7e10",
      "userId": "b7cb565a-d045-44d3-a2cf-8870fa536611",
      "startedAt": "2026-10-27T21:00:00.500+09:00",
      "apps": [
        { "name": "YouTube", "minutes": 30 },
        { "name": "TikTok", "minutes": 20 }
      ],
      "purpose": "勉強"
    },
    {
      "id": "0d3e7b52-8a14-4c6f-b2e9-5f71c0a4d983",
      "userId": "b7cb565a-d045-44d3-a2cf-8870fa536611",
      "startedAt": "2026-10-28T13:15:02.000+09:00",
      "apps": [
        { "name": "Instagram", "minutes": 60 },
        { "name": "LINE", "minutes": 45 }
      ],
      "purpose": null
    }
  ],
  "demo": false
}
```

この 2 件から、まとめ画面には次のように表示される。

- 今週の合計: 2 時間 35 分
- アプリ別: Instagram 60 分 / LINE 45 分 / YouTube 30 分 / TikTok 20 分
- カレンダー: 27 日（YouTube・TikTok）、28 日（Instagram・LINE）に印が付き、タップすると各アプリの時間帯と目的が出る

## キャラクター（slime.glb）

Blender で作ったスライムを [`public/models/slime.glb`](public/models/slime.glb) に置いている。表示は [`src/components/Slime.jsx`](src/components/Slime.jsx)。
Blender で作り直した時は、同じ名前で上書きすればそのまま反映される（下の決まりを守っていればコードの変更は不要）。

### モデルの決まり

| 項目 | 決まり |
|---|---|
| 大きさ・向き | 高さ 1.0・原点は足元（底の中心）。正面は Blender の正面ビュー（three.js では +Z） |
| アクション | `Idle`（ループ）・`Walk`（ループ。その場で跳ねるだけで前進は入れない）・`Jump`（1回） |
| シェイプキー | `MouthOpen`（0 = 閉じる / 1 = 開く）。どのアクションでも動かさない（アプリ側で操作する） |
| マテリアル | Principled BSDF のみ。マテリアルごとにメッシュが分かれるので、`MouthOpen` は全メッシュにかける |
| マテリアル名 | 体は `SlimeBody`（色を変える・滑らかにする・王冠の位置に使う）、口の中は `SlimeMouth`（チケットが口の位置を追いかけるのに使う）。作り直す時もこの名前のままにする |

### いつどの動きをするか

| 場面 | 動き |
|---|---|
| 普段 | `Idle` |
| ロック中（固定時間では予定の時間中で、一時解除していない時） | `Walk` で左右に行ったり来たり（前進と向きはアプリ側で動かす） |
| 「おめでとう！」が出た時 / キャラをタップした時 / 色が上がった時 | `Jump` を 1 回（口を開ける）→ 終わる少し前から元の動きに戻る |
| お休みチケットを使った時（自分でロック） | 下の「チケットを食べる」 |
| 色が変わった時 | 体の色をなめらかに変える。銀色の時だけ、少し金属っぽく光らせる |
| 王冠をかぶる時 | 体のいちばん高い頂点を毎フレーム追いかけて頭に乗せる（歩き・ジャンプでもずれない）。かぶる・外れる時はふわっと大きさを変える |

**チケットを食べる**: 判定のお知らせを出す前に、使った枚数だけ 🎫 が右下から弧を描いて口へ飛び、スライムが食べる（2 枚以上は少し間をあけて順番に）。食べている間は歩くのをやめて正面を向き、口を大きく開ける。食べたら「もぐっ」と縦に弾み、食べ終わってから「🎫 お休みチケットで守りました」を出す。「おめでとう！」が出ている時は、閉じてから食べる。

利用者が見ている時に食べるように:
- 判定の結果は保存しておき、食べる前にアプリを閉じても次に開いた時に食べる
- メイン画面が表示されるまで待つ。画面が裏に回っている間は描画が止まるので進まず、見えるようになってから 0.6 秒おいて飛び始める（止まっていた時間で一気に進めない）
- 3D の読み込みに失敗した時と、画面が見えているのに 15 秒たっても終わらない時だけ、食べたことにして先へ進む

### その他

- **表面はアプリ側で滑らかにしている**: 読み込んだ時に体の面を細かく分けて丸める（Loop 細分割。[`src/components/subdivide.js`](src/components/subdivide.js)）。Blender のサブディビジョンと同じ考え方で、骨の重みとシェイプキーも引き継ぎ、底の平らな面のふち（法線が分かれた辺）と口のふちは角として残す。体の法線は細分割の後に計算し直す（目と口の中はモデルの法線のまま）。細かさは `Slime.jsx` の `SMOOTH`（1回ごとに面が4倍、0 で Blender のまま）。Blender 側でサブディビジョンを適用して書き出した場合は `SMOOTH` を 0 にする（二重にかけると重くなるだけ）
- **歩く幅は自動で決まる**: キャラは丸い枠の中に表示される。`Walk` と `Jump` でいちばん変形した姿勢でも枠の円からはみ出さない範囲を計算し、その中だけを歩く。計算に使うスライムの外形と変形量は `Slime.jsx` の `PROFILE` / `POSES` にある。**モデルの形や動きを大きく変えた時は、この値も測り直すこと**
- 大きさ（`SCALE`）・歩く幅の上限・歩く速さ・口の開き具合・銀色の質感・王冠をかぶせる深さ・チケットの飛び方は、`Slime.jsx` の先頭の定数で変えられる。色そのものは `habit.js` の `COLORS`
- アクションが無い場合はその動きを飛ばすので、アクションを減らしてもエラーにはならない
- モデルの読み込みに失敗しても、キャラの部分が空になるだけで画面は止まらない

## 未決定のこと・バックエンドに頼むこと

| 項目 | 今の状態 | どうしたいか |
|---|---|---|
| 一時解除の長さ | 申請の時に長さを選べないので、30分の1種類だけ | **バックエンドに依頼**: `POST /unlocks` で分数を送れるようにしてほしい。できたら 20分・30分・1時間のチケットに分ける（1時間がいちばん高い） |
| 一時解除の設定の初期値 | 未確認。初期値より緩い設定は、始めた翌朝の承認まで効かない | **バックエンドに確認**: 初期値（1回の長さ・1日の回数・待ち時間） |
| 動いているタイマーをもう一度始めた時 | 仕様に無いので、アプリでは始めない | 仕様に入ったら、延長などに使うか考える |
| ルールの API | 仕様（案）はあるが、サーバーにはまだログインしか無い | 実装されたら `.env` で本物につなぐ |
| ログイン画面 | メールアドレスとパスワードのモックのまま | Google ログイン（`/auth/google/start`）に作り直す |
| Cloudflare との連携画面 | 説明ページでは「つなぎ方はログインの後に案内します」としているが、その画面はまだ無い | 連携（`/cloudflare/connect`）・初期設定（`/cloudflare/setup`）・手でやる手順（`manualSteps`）を出す画面を作る |
| カタログに無いアプリ（Facebook・Threads） | ドメイン1つで止めているので、一部が使えることがある | カタログに入れてもらうか、ドメインを足す |
| 「その日の終わり」 | 23:59 まで（1分止まらない） | サーバーで 24:00 を書けるようになれば直す |
| 判定の記録 | 毎日の目標の判定・一時解除を使った記録は端末にある（別の端末の操作は入らない、時計を変えるとごまかせる） | 保存先ができたらサーバー側で持つ |
| 別の端末で始めたロック | 開始の時に防ぐだけで、メイン画面の一覧には出ない | `GET /status` から一覧を作る |
| WARP を切られた時 | 検知できない（切ればブロックは効かない） | 検知できるならバックエンドに頼む |
