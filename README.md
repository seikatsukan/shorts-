# SNS Blocker Web

SNS などのアプリの利用を、スマホからサーバー（cf-rules-api）に頼んで一定時間ブロックする Web アプリ（スマホ向け）。
ブロックはサーバーがユーザーの Cloudflare Zero Trust に反映し、スマホの 1.1.1.1 アプリ（WARP）の通信で効く。
ロックをやりきるとコインが貯まり、毎日の目標を続けるとキャラクター（スライム）の色が変わる。

## 起動方法

```bash
npm install
npm run dev
```

`.env` が無い間は、**モック**（ブラウザ内の仮サーバー。下の「サーバーとのやりとり」の決まりどおりに応答する）で動く。

本物のサーバーにつなぐ場合は、プロジェクト直下に `.env` を作って次の2行を書く。

```
VITE_API_BASE=/api
API_PROXY_TARGET=http://localhost:8787
```

- `VITE_API_BASE`: API の場所。仕様どおり画面と同じオリジンの `/api` 以下
- `API_PROXY_TARGET`: 開発サーバー（Vite）が `/api` と `/auth` を流す先。手元の cf-rules-api（`uv run pywrangler dev`）なら `http://localhost:8787`、デプロイ済みのものはその URL（バックエンド担当に聞く）（[`vite.config.js`](vite.config.js)）
- ログインは Cookie（`session`）で続くので、画面と API を同じオリジンに見せる必要がある（cf-rules-api の README の決まり）
- **ログイン画面はまだサーバーにつないでいない**。今のサーバーは偽の Google ログインだけなので、ブラウザで `http://localhost:5173/auth/google/start` を一度開くと、テスト用のユーザーでログインした状態（Cookie）になる

### スマホで試す

```bash
npm run dev -- --host
```

表示された `Network: http://192.168.x.x:5173/` をスマホのブラウザで開く（スマホと PC は同じ Wi-Fi に接続）。
http で開いても動くように、ID の生成などは https 専用の機能（`crypto.randomUUID` など）に頼らない作りにしている（[`src/utils.js`](src/utils.js)）。

## 全体の流れ

```
スマホ（このアプリ）                     サーバー（cf-rules-api）        保存先（未定）
 ① アプリ・時間・目的を選ぶ
 ② スタート ── アプリごとにタイマーを開始 ─▶ Cloudflare に反映
             ◀──── 終わる時刻 ─────────
 ③ 記録を送る ──────────────────────────────────────────────▶ 保存
 ④ カウントダウン表示（サーバーの時刻基準）
 ⑤ 終了 → 「おめでとう！」＋コイン付与
 ⑥ まとめ画面 ◀──────────── 期間を指定して記録を取得 ─────────── 
```

- 一度始めたロックは**キャンセルできない**。スマホからは止める操作を送らない（サーバーでも、ルールを緩める変更は翌朝以降に本人が承認するまで反映されない）。
- 目的はサーバーには送らず、保存先にだけ送る。

## サーバーとのやりとり

実装: [`src/api.js`](src/api.js)

取り決めは `seikatsukan/api-spec` の `openapi.yaml`（v0.2.0 の案）。**バックエンドは変えられないので、こちらが合わせる。**

| 決まり | 内容 |
|---|---|
| 場所 | 画面と同じオリジンの `/api` 以下 |
| ログイン | `/auth` 以下で付く Cookie `session`（`fetch` が自動で送る）。無い・切れている時は 401 `UNAUTHORIZED` |
| 項目名・時刻 | JSON は camelCase、時刻は `2026-10-30T21:30:00+09:00` の形 |
| エラー | 常に `{ "code", "message", "details" }`。`message` はそのまま画面に出せる日本語なので、そのまま表示する |

### ロックのしかた（アプリごとに集中タイマーのルールを1つ持ち、使い回す）

サーバーには「今からこのアプリを○分」という API は無く、「ルール（対象と時間の決め方）を作る」「timer のルールを始める」が別々にある。そこでアプリごとに timer のルールを1つ作り、ロックのたびにそのルールを選んだ分数で始める。

1. `GET /options`・`GET /rules`・`GET /status` を同時に呼び、アプリ ID・今あるルール・サーバーの現在時刻を取る
2. 選んだアプリのうち、**ロック中（`timerEndsAt` が未来）のものが1つでもあれば何も始めずにエラー**。動いているタイマーをもう一度始めた時の動きは仕様に無いため（画面でもロック中のアプリは選べない。これは別の端末で始めていた時のため）
3. まだルールが無いアプリだけ `POST /rules` で作る。オフになっているルールは `PATCH /rules/{ruleId}` で `{"enabled": true}` にする（どちらも「厳しくする変更」なのですぐ反映）
4. アプリごとに `POST /rules/{ruleId}/timer` を `{"durationMinutes": 選んだ分数}` で呼ぶ。返ってきたルールの `timerEndsAt` が終わる時刻

- **ルールは消さない**。消すのは「緩める変更」で翌朝以降の承認が要るため、毎回作って消す形にはしない。終わったタイマーのルールは、そのアプリを次にロックする時にまた使う
- 1回のスタートで複数のアプリを選べ、アプリごとに時間が違ってもよい（ルールがアプリごとなので、それぞれ別のタイマーになる）
- 同じアプリかどうかは、ルールの名前ではなく `target` の中身（`apps` / `domains`）で見分ける

### アプリの指定（`target`）

サーバーのカタログ（`GET /options` の `apps`）にあるアプリは **ID** で、無いアプリは **ドメイン** で送る。

| アプリ | 送る `target` |
|---|---|
| YouTube / TikTok / Instagram / X | `{"type": "sites", "apps": ["youtube"], "domains": [], "categoryIds": []}`（ID は `displayName` が同じものを探す） |
| Facebook / Threads（カタログに無い） | `{"type": "sites", "apps": [], "domains": ["facebook.com"], "categoryIds": []}`（[`apps.js`](src/data/apps.js) の `DEFAULT_APPS` のドメイン） |
| カスタムアプリ | `{"type": "sites", "apps": [], "domains": ["line.me"], "categoryIds": []}`（入力されたドメイン。`https://`・`www.`・パスを取り除いた形） |

### 時刻

- カウントダウンは `timerEndsAt` を終わる時刻、そこから分数を引いた時刻を始まった時刻として表示する
- スマホの時計がずれていてもサーバーの時刻に合わせられるよう、`GET /status` の `now` との差でずれを補正する（通信にかかった時間の半分も差し引く）

### うまくいかなかった時

| 場面 | 画面 |
|---|---|
| ロック中のアプリが含まれていた | 何も始めずに「○○ はすでにロック中です」 |
| カスタムアプリのルールを作る時に 422 `VALIDATION_ERROR` | 何も始めずにアプリ選択画面へ戻り、そのアプリの名前・ドメインの修正画面を開く |
| **一部のアプリだけタイマーを始められた** | 始められたアプリはロックとして登録する（始めたタイマーは止められないため）。確認画面には始められなかったアプリだけ残し、「○○ はロックを始めました。△△ は始められませんでした（理由）」と出して「もう一度試す」を押せるようにする |
| 1つも始められなかった | サーバーの `message`（例: 409 `CLOUDFLARE_NOT_CONNECTED` の「Cloudflare と連携してください」）を出して「もう一度試す」 |
| JSON の無い HTTP エラー | 「サーバーエラー (500)」 |
| 15 秒以内に応答が無い／つながらない | 「サーバーから応答がありません」／「サーバーに接続できません」 |

### モックの動き

`VITE_API_BASE` が未設定の時は、[`src/api.js`](src/api.js) の中のモックが上で使うエンドポイントに仕様どおりの形で答える（1回 0.25 秒）。

- カタログは cf-rules の `get_catalog()` と同じ（X・YouTube・Instagram・TikTok・LINE）
- ルールは `localStorage` の `sns-blocker:mock-api` に保存する（再読み込みしても、動いているタイマーが残る）
- ドメインの形が cf-rules の決まり（英小文字・数字・`-`・`_` を `.` でつないだもの）に合わない時は 422 `VALIDATION_ERROR`
- 動いているタイマーをもう一度始めると 409 `TIMER_RUNNING`（仕様に無いので仮。アプリからは呼ばない）
- **一部だけ失敗する場面を試す**: `localStorage` の `sns-blocker:mock-api-fail` に `["Facebook"]` のようにルール名を入れると、そのルールのタイマーを始める時に 502 `CLOUDFLARE_API_ERROR` を返す

## 保存先とのやりとり

実装: [`src/storage.js`](src/storage.js)

保存先（DB・クラウドなど）は**未定**。今は端末の `localStorage` に保存するモックで動いている。
保存先が決まったら、`saveRecord` と `fetchRecords` の中身を API 通信に置き換えるだけでよい（呼び出し側は変更不要）。

### 記録を送る `saveRecord(record)`

- **いつ**: サーバーでタイマーを始められた時（ロック開始時）。ロックはキャンセルできないので、開始時点で確定とする。
- **単位**: ロックを 1 回スタートするごとに 1 件。複数アプリをまとめてロックした時は `apps` に並ぶ。

| 項目 | 型 | 内容 |
|---|---|---|
| `id` | 文字列 | 記録 ID（スマホで作る UUID） |
| `userId` | 文字列 | アカウント ID（下記） |
| `startedAt` | 日時文字列 | 開始日時（サーバーのタイマーの開始時刻） |
| `apps` | 配列 | ロックしたアプリ |
| `apps[].name` | 文字列 | アプリ名 |
| `apps[].minutes` | 数値 | 制限時間（分） |
| `purpose` | 文字列 / `null` | 目的（「勉強」「昼寝」「スポーツ」、カスタム入力の文字）。スキップした時は `null` |

```json
{
  "id": "db88aa66-5576-4251-978a-2d7eda1fefe8",
  "userId": "b7cb565a-d045-44d3-a2cf-8870fa536611",
  "startedAt": "2026-10-27T12:58:04.576Z",
  "apps": [
    { "name": "LINE", "minutes": 30 },
    { "name": "YouTube", "minutes": 20 }
  ],
  "purpose": "勉強"
}
```

- 各アプリの終了時刻は `startedAt + minutes` で求められるので保存しない。
- **`userId` について**: ログイン中のアカウント ID（下の「アカウント（認証）」が返す `userId`）。
- 送信に失敗してもロックや画面表示は止めない（コンソールにエラーを出すだけ）。

### 記録を取得する `fetchRecords({ userId, from, to })`

まとめ画面（今週 / 今月のグラフ、カレンダー）を表示する時に呼ぶ。

| 引数 | 内容 |
|---|---|
| `userId` | このアカウントの記録だけ取得する |
| `from` | 期間の始まり（この日時を含む） |
| `to` | 期間の終わり（この日時を含まない） |

- `startedAt` が `from` 以上 `to` 未満の記録を、上の「送る記録」と同じ形の配列で返す。
- 呼ばれ方: 週（月曜 0:00〜翌週月曜 0:00）、月（1 日 0:00〜翌月 1 日 0:00）、カレンダーの表示月。いずれも端末の時間帯で区切る。
- 戻り値は `{ records: [...], demo: false }`。`demo` はモック専用で、保存済みの記録が 1 件も無い時に見た目確認用のデモデータを返したことを示す。本番の保存先では常に `false` でよい。

## アカウント（認証）

実装: [`src/auth.js`](src/auth.js)

認証サーバーは**未定**。今は端末の `localStorage` にアカウントを保存するモックで動いている（パスワードは SHA-256 でハッシュ化して保存）。
認証サーバーができたら、`signUp` と `logIn` の中身を API 通信に置き換えるだけでよい（呼び出し側は変更不要）。

- **いつ**: 説明ページの Step 3 で「アカウントを作成」または「ログイン」を押した時。
- **成功したら**: 返ってきた `userId` / `email` をログイン状態として端末に保存し、メイン画面へ進む。以後、保存先への記録の送信・取得にこの `userId` を使う。
- **ログアウト**: メイン画面のメニューから。端末のログイン状態を消して説明ページに戻る。

### スマホ → 認証サーバー（新規登録 / ログインとも同じ形）

```json
{
  "email": "test@example.com",
  "password": "password123"
}
```

- 新規登録の時、パスワードは 8 文字以上（スマホ側でも確認してから送る）。

### 認証サーバー → スマホ（成功）

```json
{
  "userId": "85e212bd-5eeb-42db-be42-e004749b19f6",
  "email": "test@example.com"
}
```

### 認証サーバー → スマホ（失敗）

失敗の理由を画面に表示する。モックでは次の 2 つ。

| 場面 | 表示する文 |
|---|---|
| 新規登録で、メールアドレスがもう使われている | このメールアドレスはすでに登録されています |
| ログインで、メールアドレスかパスワードが違う | メールアドレスかパスワードが違います |

通信そのものに失敗した時は「通信に失敗しました。もう一度お試しください」と表示する。

## JSON の例（場面ごと）

日時は日本時間（`+09:00`）で書いている。ルール ID などはサーバーが付ける値の例。

### 例 1: 初めて YouTube と Facebook をロック（目的あり）

YouTube を 30 分、Facebook を 20 分、目的「勉強」でスタートした場合。どちらもまだルールが無い。

**① スマホ → サーバー**（`GET /options`・`GET /rules`・`GET /status` を同時に）

`GET /options` の応答（抜粋）

```json
{ "apps": { "youtube": { "displayName": "YouTube", "domains": ["youtube.com", "youtu.be"] } }, "categories": {}, "webPushPublicKey": null }
```

`GET /rules` の応答は `[]`、`GET /status` の応答（抜粋）は次のとおり。

```json
{ "now": "2026-10-30T21:00:00+09:00", "timezone": "Asia/Tokyo", "blockingRuleIds": [] }
```

**② スマホ → サーバー**（ルールを作る。`POST /rules` を1つずつ）

```json
{ "name": "YouTube", "schedule": { "type": "timer", "durationMinutes": 30 }, "target": { "type": "sites", "apps": ["youtube"], "domains": [], "categoryIds": [] } }
```

```json
{ "name": "Facebook", "schedule": { "type": "timer", "durationMinutes": 20 }, "target": { "type": "sites", "apps": [], "domains": ["facebook.com"], "categoryIds": [] } }
```

応答は `{ "applyMode": "immediate", "rule": { "id": "rule_3f9a1c", ... } }`。

**③ スマホ → サーバー**（タイマーを始める）

`POST /rules/rule_3f9a1c/timer`

```json
{ "durationMinutes": 30 }
```

応答（ルール。抜粋）

```json
{ "id": "rule_3f9a1c", "name": "YouTube", "enabled": true, "schedule": { "type": "timer", "durationMinutes": 30 }, "timerEndsAt": "2026-10-30T21:30:00+09:00", "pendingChange": null }
```

Facebook も同じように `POST /rules/{Facebook のルール ID}/timer` に `{"durationMinutes": 20}` を送る。

**④ スマホ → 保存先**（記録を送る）

```json
{
  "id": "6f1c2a9e-3b7d-4e2a-9c41-0a8f5d2b7e10",
  "userId": "b7cb565a-d045-44d3-a2cf-8870fa536611",
  "startedAt": "2026-10-30T21:00:00.000+09:00",
  "apps": [
    { "name": "YouTube", "minutes": 30 },
    { "name": "Facebook", "minutes": 20 }
  ],
  "purpose": "勉強"
}
```

### 例 2: 次の日にまた YouTube をロック（ルールを使い回す）

YouTube を 60 分、カスタムで追加した LINE（`line.me`）を 45 分、目的なしでスタートした場合。

- `GET /rules` に YouTube のルール（`timerEndsAt` は過去）があるので、作らずに `POST /rules/rule_3f9a1c/timer` に `{"durationMinutes": 60}` を送る
- LINE はカスタムなのでドメインで探す。まだ無いので `POST /rules` で `"target": {"type": "sites", "apps": [], "domains": ["line.me"], "categoryIds": []}` のルールを作ってから始める
- 保存先には `"purpose": null` で送る

### 例 3: ロック中のアプリが含まれていた

YouTube のタイマーが別の端末で始まっていた（`GET /rules` の YouTube のルールの `timerEndsAt` が未来）。

→ ルールを作ることもタイマーを始めることもせず、「YouTube はすでにロック中です」と出す。保存先には何も送らない。

### 例 4: 一部のアプリだけ始められなかった

YouTube は始められたが、Facebook の `POST /rules/{ruleId}/timer` が次のエラーを返した。

```json
{ "code": "CLOUDFLARE_API_ERROR", "message": "Cloudflare への反映に失敗しました。しばらくしてからもう一度お試しください", "details": { "retryable": true } }
```

→ YouTube はロックとして登録し、保存先にも YouTube だけの記録を送る。確認画面には Facebook だけを残して「YouTube はロックを始めました。Facebook は始められませんでした（Cloudflare への反映に失敗しました。…）」と出す。「もう一度試す」で Facebook だけを始め直す（別の記録になる）。

### 例 5: Cloudflare とまだ連携していない

最初のタイマーを始める時に 409 が返り、1つも始められなかった。

```json
{ "code": "CLOUDFLARE_NOT_CONNECTED", "message": "Cloudflare と連携してください", "details": null }
```

→ 「Cloudflare と連携してください」を出し、「もう一度試す」を押せるようにする。保存先には何も送らない。作ったルールはそのまま残り、次に使われる。
### 例 6: 保存先から記録を取得（まとめ画面）

10 月 26 日（月）〜 11 月 1 日（日）の「今週」を表示する場合。

**スマホ → 保存先**（取得の条件）

```json
{
  "userId": "b7cb565a-d045-44d3-a2cf-8870fa536611",
  "from": "2026-10-26T00:00:00.000+09:00",
  "to": "2026-11-02T00:00:00.000+09:00"
}
```

`from` は含み、`to` は含まない（月曜 0:00 から翌週月曜 0:00 の手前まで）。

**保存先 → スマホ**（`startedAt` が期間内の記録を、送った時と同じ形で返す）

```json
{
  "records": [
    {
      "id": "6f1c2a9e-3b7d-4e2a-9c41-0a8f5d2b7e10",
      "userId": "b7cb565a-d045-44d3-a2cf-8870fa536611",
      "startedAt": "2026-10-27T21:00:00.500+09:00",
      "apps": [
        { "name": "YouTube", "minutes": 30 },
        { "name": "TikTok", "minutes": 20 }
      ],
      "purpose": "勉強"
    },
    {
      "id": "0d3e7b52-8a14-4c6f-b2e9-5f71c0a4d983",
      "userId": "b7cb565a-d045-44d3-a2cf-8870fa536611",
      "startedAt": "2026-10-28T13:15:02.000+09:00",
      "apps": [
        { "name": "Instagram", "minutes": 60 },
        { "name": "LINE", "minutes": 45 }
      ],
      "purpose": null
    }
  ],
  "demo": false
}
```

記録が無い期間は `"records": []` を返す。

この 2 件から、まとめ画面には次のように表示される。

- 今週の合計: 2 時間 35 分
- アプリ別: Instagram 60 分 / LINE 45 分 / YouTube 30 分 / TikTok 20 分
- カレンダー: 27 日（YouTube・TikTok）、28 日（Instagram・LINE）に印が付き、タップすると各アプリの時間帯と目的が出る

## アプリ内のルール

| 項目 | ルール | 場所 |
|---|---|---|
| コイン | **10 分ごとに 1 枚**。1 回のスタートで複数アプリをロックした時は、**一番長い制限時間**で計算する（例: 30 分 + 60 分 → 6 枚）。そのスタートのロックが全部終わった時に付与する。もらったコインは「持っているコイン」になり、**お休みチケットを買うのに使う**（1 枚 🪙10） | [`src/data/apps.js`](src/data/apps.js) `coinsFor` / [`AppContext.jsx`](src/store/AppContext.jsx) |
| 進化・退化 | 下の「毎日の目標（21日で銀色）」を参照。スライムの**色**で表す（大きさは一定） | [`src/habit.js`](src/habit.js) |
| 初めての利用者 | ログインしていない時は `/` で説明ページ（PCの準備 → 使い方 → アカウント）を表示する。ログイン中はメイン画面へ。ログインしていないのにメイン画面などを開くと `/` に戻す | [`src/App.jsx`](src/App.jsx) `Entry` / `RequireAccount` |

## 毎日の目標（21日で銀色）

実装: [`src/habit.js`](src/habit.js)（判定のルール） / [`src/store/AppContext.jsx`](src/store/AppContext.jsx)（いつ判定するか） / [`src/pages/Home.jsx`](src/pages/Home.jsx)（表示）

SNS を見ない習慣づくりのために、毎日の目標を続けるとスライムの色が変わる。

| 項目 | ルール |
|---|---|
| 1日の目標 | 1 日にロックする時間を利用者が決める（30分 / 1時間 / 1時間30分 / 2時間 / 3時間 / カスタム 10〜720 分）。初めてメイン画面を開いた時に決め、メニューの「1日の目標」で変えられる。変えた目標は今日の判定から使う |
| 1日の成功 | その日（0時〜24時、端末の時間帯）にロックした時間の合計が目標以上なら成功。**実際に経過した分だけ**数える（60分のロックを始めた直後は 0 分。経過するにつれて増える）。同じ時間に複数のアプリをロックしても二重に数えない（30分×3アプリ＝30分）。重なったロックはまとめて数える。日をまたぐロックは 0 時で分けて両方の日に数える |
| 今日の表示 | メイン画面のカードのいちばん上に「今日の目標 ◯ / ◯分」とバーを大きく出す。バーの濃い部分は経過した分、しま模様は今のロックが終わるまでに増える分。下に今の状況を一言で出す（「あと◯分 ロックすると今日の目標を達成」「ロック中… あと◯分で達成」「ロック中。終わってもあと◯分 足りません」「✓ 今日の目標を達成しました」） |
| 進化までの道のり | カードの下に 21 日分のマスを並べ、色が変わる日（3・7・14・21 日目）に次の色の丸を置く。達成した日はその区間の色で塗り、今日のマスは点滅させる（今日達成するとここまで進む）。色が下がった時はその色の位置まで戻る。横に「あと ◯日 で ●紫」と出す |
| 色の段階 | 水色 → 緑 → 青 → 紫 → **銀**（`COLORS`） |
| 進化 | 連続で成功して、**3日・7日・14日・21日**目に 1 つ上の色になる（`STEP_DAYS` = 3, 4, 7, 7 日ずつ）。上がる時にジャンプする |
| お休みチケット | 目標に届かなかった日に自動で使い（使った時はスライムがチケットを食べる）、その日は何も起きない（色も連続記録もそのまま）。**無料**: 1 週間（月曜〜日曜）に 1 枚。持ち越しはできない。**コインで買う**: 1 枚 🪙10（`TICKET_PRICE`）。3 枚まで持てる（`MAX_EXTRA_TICKETS`）。メイン画面の 🎫 から買う。使う順は無料 → 買った分 |
| 退化 | チケットが無い時に目標に届かなかったら、1 つ下の色に戻り、連続記録と次の色までの日数は 0 に戻る。水色より下にはならない |
| 失敗が続いた時 | **下がるのは最初の 1 回だけ**。その後も失敗が続く間は、連続記録 0 のまま色はそれ以上下がらず、チケットも使わない（守るものが無いため）。次に成功すると普通に戻る。こうすると、毎日アプリを開いて失敗しても、開かずに放っておいても結果が同じになる（「失敗した日は開かない方が得」にならない） |
| 銀色の後 | 毎日の目標は続く。失敗すると紫に戻る |
| 王冠（隠し要素） | 銀色になってから `CROWN_DAYS`（3）日続けて成功すると、スライムが王冠をかぶる（`hasCrown`）。お休みチケットの日は外れないが日数にも数えない。失敗して紫に戻ると外れ、また銀色になってから3日で再びかぶる。**ユーザーには何も知らせない**（お知らせ・説明文・ふりかえりに出さない） |
| 判定のタイミング | 今日の分は、経過した時間が目標に届いた時点ですぐ成功にする。届かなかった日は、日付が変わってから失敗として判定する。アプリを開かなかった日も、次に開いた時に 1 日ずつまとめて判定し、結果をポップアップで知らせる |
| 判定に使う記録 | 保存先の記録（`fetchRecords`）。モックのデモデータは使わない（`allowDemo: false`） |

- まだ知らせていない判定の結果は、アカウントごとに `habitEvents` として保存する（アプリを閉じても消えない）。お知らせの「OK」で空にする。食べたチケットには `eaten: true` を付ける。
- 判定の状態はアカウントごとに `habit`（`goal` / `stage` / `progress` / `streak` / `settledUntil` / `ticketsUsed` / `extraTickets` / `failing`）として保存する。
- 判定の結果は、今日の目標を達成した時や、しばらくぶりに開いた時にポップアップで知らせる。見出しは中身に合わせる（✨ 進化した！ / 💧 色が1つ戻りました / 🎯 今日の目標を達成！ / 🎫 お休みチケットで守りました / 💧 目標に届きませんでした / 📅 前回からの結果）。
- 結果のポップアップでは、失敗が続いた日を「10/24〜10/28 目標に届かず（色はこれ以上下がりません）」のように 1 行にまとめる。保存先ができたら、ここもサーバー側で持つのが望ましい（端末の時計を変えると判定をごまかせるため）。
- 開発中（`npm run dev`）だけ、メイン画面に「🧪 1日成功」「🧪 1日失敗」「🧪 コイン+10」のテスト用ボタンが出る。本番のビルドには入らない。

## キャラクター（slime.glb）

Blender で作ったスライムを [`public/models/slime.glb`](public/models/slime.glb) に置いている。表示は [`src/components/Slime.jsx`](src/components/Slime.jsx)。
Blender で作り直した時は、同じ名前で上書きすればそのまま反映される（下の決まりを守っていればコードの変更は不要）。

### モデルの決まり

| 項目 | 決まり |
|---|---|
| 大きさ・向き | 高さ 1.0・原点は足元（底の中心）。正面は Blender の正面ビュー（three.js では +Z） |
| アクション | `Idle`（ループ）・`Walk`（ループ。その場で跳ねるだけで前進は入れない）・`Jump`（1回） |
| シェイプキー | `MouthOpen`（0 = 閉じる / 1 = 開く）。どのアクションでも動かさない（アプリ側で操作する） |
| マテリアル | Principled BSDF のみ。マテリアルごとにメッシュが分かれるので、`MouthOpen` は全メッシュにかける |
| 法線 | カスタム法線を使っているので、アプリ側で法線を計算し直さない（`computeVertexNormals()` を呼ばない） |

### いつどの動きをするか

| 場面 | 動き |
|---|---|
| 普段 | `Idle` |
| ロック中 | `Walk` で左右に行ったり来たり（前進と向きはアプリ側で動かす） |
| 「おめでとう！」が出た時 / キャラをタップした時 / 色が上がった時 | `Jump` を 1 回（口を開ける）→ 終わる少し前から元の動きに戻る |
| お休みチケットを使った時 | 判定のお知らせを出す前に、使った枚数だけ 🎫 が右下から弧を描いて口へ飛び、スライムが食べる（2 枚以上は少し間をあけて順番に）。食べている間は歩くのをやめて正面を向き、口を大きく開ける（`MouthOpen` = 1）。食べたら「もぐっ」と縦に弾む。食べ終わってから「🎫 お休みチケットで守りました」を出す。「おめでとう！」が出ている時は、閉じてから食べる。**利用者が見ている時に食べるように**: 判定の結果は保存しておき（食べる前にアプリを閉じても、次に開いた時に食べる）、メイン画面が表示されるまで待つ。画面が裏に回っている間は描画が止まるので進まず、見えるようになってから 0.6 秒おいて飛び始める（止まっていた時間で一気に進めない）。3D の読み込みに失敗した時と、画面が見えているのに 15 秒たっても終わらない時だけ、食べたことにして先へ進む |
| 色が変わった時 | 体（マテリアル `SlimeBody`）の色をなめらかに変える。銀色の時だけ、少し金属っぽく光らせる |
| 王冠をかぶる時 | 体のいちばん高い頂点（`SlimeBody`）を毎フレーム追いかけて頭に乗せる（歩き・ジャンプでもずれない）。かぶる・外れる時はふわっと大きさを変える |

- アクションが無い場合はその動きを飛ばすので、アクションを減らしてもエラーにはならない。
- **歩く幅は自動で決まる**: キャラは丸い枠の中に表示される。大きさごとに、`Walk` と `Jump` でいちばん変形した姿勢でも枠の円からはみ出さない範囲を計算し、その中だけを歩く（大きい段階ほど歩く幅は狭くなる）。計算に使うスライムの外形と変形量は `Slime.jsx` の `PROFILE` / `POSES` にある。**モデルの形や動きを大きく変えた時は、この値も測り直すこと**。
- **表面はアプリ側で滑らかにしている**: 読み込んだ時に体（`SlimeBody`）の面を細かく分けて丸める（Loop 細分割。[`src/components/subdivide.js`](src/components/subdivide.js)）。Blender のサブディビジョンと同じ考え方で、骨の重みとシェイプキーも引き継ぎ、底の平らな面のふち（法線が分かれた辺）と口のふちは角として残す。細かさは `Slime.jsx` の `SMOOTH`（1回ごとに面が4倍、0 で Blender のまま）。Blender 側でサブディビジョンを適用して書き出した場合は `SMOOTH` を 0 にする（二重にかけると重くなるだけ）。
- 大きさ（`SCALE`）・歩く幅の上限・歩く速さ・口の開き具合・銀色の質感・王冠をかぶせる深さ・チケットの飛び方（時間・出発点・弧の高さ・大きさ）は、`Slime.jsx` の先頭の定数で変えられる。色そのものは `habit.js` の `COLORS`。
- モデルを作り直す時は、体のマテリアル名を `SlimeBody`（色を変えるのに使う）、口の中のマテリアル名を `SlimeMouth`（チケットが口の実際の位置を追いかけるのに使う）のままにすること。
- モデルの読み込みに失敗しても、キャラの部分が空になるだけで画面は止まらない。
